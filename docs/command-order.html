GSD Command Order

One phase, from claiming the number to merging it back. Everything in the middle happens inside that phase's own worktree.

The whole loop

gsd-start "description" on develop
/gsd-spec-phase Nif scope is fuzzy
/gsd-discuss-phase N agree the decisions
/gsd-ui-phase Nif it has screens
/gsd-plan-phase N write the plan
/gsd-execute-phase N build it
/gsd-verify-work N did it deliver?
/gsd-ui-review Nif it has screens
/gsd-code-review N bugs + quality
/gsd-validate-phase Nmissing tests
/gsd-secure-phase N security — every phase
gsd-finish merge + clean up

What each one is for

  1. 1 gsd-start "description"on develop Picks the next free phase number, makes the worktree, and opens a new session inside it. Run it from the main checkout. Everything after this happens in the new session.
  2. 2 /gsd-spec-phase Noptional Only when you are not yet sure what the phase delivers. It pins the scope down before anyone argues about how. Skip it when the roadmap line is already clear.
  3. 3 /gsd-discuss-phase N Asks you the open questions and records your answers. This is where the real decisions get made, so do not rush it.
  4. 4 /gsd-ui-phase Nscreens only Agrees the screens before anyone writes them. Your own rule says UI gets agreed before implementation — this is the step that does it.
  5. 5 /gsd-plan-phase N Turns the decisions into numbered plans with tasks. Add --research to refresh the research first.
  6. 6 /gsd-execute-phase N Builds it, one wave at a time, committing as it goes. The long one.
  7. 7 /gsd-verify-work N Walks the phase's promises with you and checks each one really happened. Catches "the task is ticked but the feature is not there".
  8. 8 /gsd-code-review N Reads the code the phase changed, looking for bugs and mess. Add --fix to apply what it finds.
  9. 9 /gsd-ui-review Nscreens only Scores the screens that were built against six quality checks. Do it after the code review, not before.
  10. 10 /gsd-secure-phase Nevery phase Checks the security protections in the plan actually exist in the code. Run it for every phase, not only the ones that look security-related.
  11. 11 /gsd-validate-phase Noptional Finds requirements with no test covering them, and writes the missing tests.
  12. 12 gsd-finish Merges the branch back, pushes, and deletes the worktree. Run it last — it removes the folder you are standing in.

Not part of the loop

CommandUse it when
/gsd-quickA small job that does not deserve a whole phase. Still commits properly.
/gsd-fastTruly tiny — a typo, one line. Three file edits at most.
/gsd-debugHunting a bug. Keeps its notes so you can stop and come back.
/gsd-progressYou forgot where you are.
/gsd-resume-workComing back to a phase after a break or a lost session.
/gsd-pause-workStopping in the middle and want to pick it up cleanly later.
/gsd-audit-uatListing every test item still waiting on you, across all phases.
/gsd-audit-milestoneChecking a finished milestone against what you originally wanted.
/gsd-complete-milestoneClosing a milestone and starting the next.

The one rule that trips people up

Every command with a phase number runs inside that phase's worktree. A guard blocks them anywhere else. The exceptions are gsd-start, which runs on develop in the main checkout, and the two audit commands, which look across all phases and also run there.
